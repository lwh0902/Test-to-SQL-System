# travel_b2b 总计划（2026-09-07）

范围只覆盖 `travel_b2b`。长期形态：认证语义上的对话内核、可钉盘看板、查数必经 Harness、A2A 按 Google 任务/工件概念自研（不引入官方 SDK）。

本文件是阶段划分和验收的权威来源。与历史 Phase 报告、pytest 全绿、HTTP 200、`SUCCESS_WITH_DATA` 单独出现冲突时，以本文件为准。

## 总原则

1. 验收只认**同一会话、真实登录、真实 `/api/chat`、真实 travel_b2b MySQL** 上的连续对话。禁止 mock Parser、禁止只打组件函数、禁止用接口 200 或「有回复」当通过。
2. 一轮通过 = 期望快照全部命中：表 `tb_orders`、指标、维度、筛选、时间范围；SQL 含对应谓词；`QueryOutcome` 与数据事实一致（条件本应无数据才允许 `SUCCESS_EMPTY`；错口径却查出数 = 失败）。
3. 应继承却丢掉的指标/时间/筛选，称为**继承断裂**，记为该轮失败，不能用「模型换了一种合理解释」抵消。
4. 澄清只在剧本写明「本轮应澄清」时算通过。剧本要求出数却澄清 = 失败。
5. 不把 pytest、单测数量、离线 oracle 写入任何阶段的完成条件。

## 阶段一：确定性追问（Query 必经 Harness）

### 要做成什么

- 会话保存**语义快照**（entity / metrics / dimensions / filters / time），不是把上一轮 Spec 塞进 prompt 指望模型整份重建。
- 追问只允许补丁：加维、加/换筛选、换时间、换指标、reset。合并、覆盖校验、编译、执行都在 **QueryHarness** 内完成。
- ApplicationService / Supervisor 只创建任务并 dispatch，不再旁路直接跑编译器。
- 聊天结果按 Spec 出图（折线/柱状），为阶段三钉盘做预览，本阶段不要求看板页。

### 验收环境

- 已登录真实用户，空间 `travel_b2b`，只读业务库为 travel_b2b mock。
- 每条会话固定同一个 `session_id`，连续提问，中间不新建会话、不重启清状态（本阶段允许进程不重启）。
- 评测剧本见文末「阶段一链路剧本」。共 **5 条会话 ×（1 首轮 + 10 次追问）**。通过率分母是 **50 次追问**，首轮单独统计但不计入 90% 分母。

### 阶段一通过线（必须同时满足）

| 指标 | 门槛 | 怎么算 |
|------|------|--------|
| 追问轮次通过率 | ≥ 90% | 50 次追问中至少 45 次快照+SQL 全中 |
| 继承断裂 | ≤ 2 次 | 「按渠道拆 / 只看酒店」等未 replace 的指标或时间丢失 |
| 首轮 | 5/5 | 五条会话的第 0 轮都必须中 |
| 主链 A | 10/10 追问 | 文末链路 A 一条都不能断，否则阶段失败（主链是产品承诺） |
| Harness | 50/50 追问 | 每轮证据或任务记录能看到 Query Agent 经 Dispatcher/Harness，而不是 ApplicationService 直接编译 |
| 禁止项 | 0 | HTTP 200、有 rows、`SUCCESS_WITH_DATA` 单独不能记通过 |

未达标不得进入阶段二。

## 阶段二：存储改成主表 + 子表

### 要做成什么

系统库仍是 MySQL。热路径停止整包 JSON：

- `session_queries` + metrics/dimensions/filters 子表，替换 `active_analysis_states.state_payload`
- 语义模型拆成 entity / metric / dimension 行，替换 `model_json` 作为运行时读源
- 聊天 `meta` 不再塞最多 200 行结果；SQL、chart 类型、`query_id` 用列
- 查数预览有界另表或刷新重查；系统库不当结果仓

双写 → 回填 → 切读 → 停写旧 JSON。

### 验收（链路，不是看表是否存在）

1. 用链路 A 跑完 11 轮，**重启后端进程**，同一 `session_id` 再追问「按供应商拆」。必须仍是 GMV + 阶段一结束时的时间/筛选，不得丢状态。
2. 打开该会话的 `session_queries` 及子表：能直接读出 metric_id、dimension、filter、时间列。禁止再依赖 `state_payload` 才能追问。
3. 随机抽 10 条 `chat_messages`：`meta` 中不得再有结果行数组。
4. 用链路 A、C 各重跑一遍，追问通过率仍 ≥ 90%，主链 A 仍 10/10。

未达标不得进入阶段三（看板没有可钉的主键）。

## 阶段三：看板（钉语义查询）

### 要做成什么

- Board / Tile：磁贴指向 `query_id`（阶段二的快照），不是一段 SQL 文本。
- 对话成功可钉盘；刷新 = 对快照发起 Query 任务，不经自然语言 Parser。
- 默认盘三块：GMV 趋势、取消率、渠道拆分（均为已发布种子指标）。
- 点磁贴可带着快照进入对话，后续追问继续走阶段一补丁。
- 草稿/未发布指标不能上盘。

### 验收

1. **口径一致：** 对话里问「2026年7到8月GMV趋势」钉盘，刷新后磁贴数字与该轮查询结果一致（允许预览行数截断，合计/趋势点必须对得上）。
2. **刷新不经 Parser：** 改一句无关闲聊后刷新磁贴，口径不变，不得被闲聊带跑。
3. **下钻链：** 从默认「渠道拆分」磁贴进入对话，连续追问 5 次（只看酒店 → 按城市 → 改成 7 月 → 改成取消率 → 按品类）。5 次必须全过（从钉盘带入的快照必须稳）。
4. **未发布指标：** 人为把某指标标成非 confirmed 后刷新，磁贴拒绝出数，不得编造。

未达标不得把看板当成可演示经营入口。

## 阶段四：A2A 任务总线硬化

### 要做成什么

参考 Google A2A 的 Task / Message / Artifact / 生命周期，不引入官方 SDK，本期不上跨进程 HTTP。

- `agent_tasks` 一行状态机：submitted → working → input-required → completed/failed
- Message 只追加；禁止 queued/running/completed 三次整包改写同一 JSON
- 时间确认 = Task `input-required`，确认后恢复同一 Task，快照不得丢
- 诊断补证必须携带已合并 Spec 进 QueryHarness，禁止无状态 `run_query_kernel` 重 plan
- 同步查数 transport 标明 in_process；诊断长任务才 queued + worker

### 验收

1. 链路 A 的 11 轮，每轮对应 1 条 Query 任务，状态终态 completed 或 input-required，没有同一任务三次整包 payload 覆盖。
2. 缺时间问「GMV 是多少」→ 停留 input-required 且 SQL 为空 → 回复「确定」后指标仍是 gmv，时间是确认后的窗口。该链 3 轮全过。
3. 先出有数据的 GMV，再明确要诊断；诊断若再查数，SQL 必须仍带上一轮指标/时间，不得换成别的表或指标。抽 3 次诊断补证，3/3 快照不丢。
4. 证据/日志不得把同进程调用写成外部 `a2a_dispatcher` 协议完成。

## 阶段一链路剧本（验收用）

每条会话先首轮，再连续 10 次追问。期望里的 GMV 默认筛选是已支付/已履约（与种子口径一致）。维度名以语义模型 ID 为准（`channel_name`、`product_type`、`city`、`supplier_name`、`product_name`）。品类「酒店」必须落到库内枚举或等价谓词，SQL 对不上仍失败。

### 链路 A（主链，10 次追问必须全过）

| 轮 | 用户说 | 必须保留/变成 |
|----|--------|----------------|
| 0 | 2026年7到8月GMV趋势 | 指标 gmv；时间 2026-07-01～2026-08-31；表 tb_orders；趋势时间粒 |
| 1 | 按渠道拆 | 仍 gmv、仍该时间；**增加** channel_name |
| 2 | 只看酒店 | 仍 gmv、时间、渠道维；**增加** 品类=酒店 |
| 3 | 换成按城市拆 | 仍 gmv、时间、酒店；维度改为 city（渠道维去掉） |
| 4 | 不要酒店限制了 | 仍 gmv、时间、城市；去掉品类筛选 |
| 5 | 时间改成2026年7月 | 仍 gmv、城市；时间改为 2026-07-01～2026-07-31 |
| 6 | 再按渠道拆一次 | 仍 gmv、7 月、城市；**加回** channel_name |
| 7 | 改成订单数 | 指标改为 order_count；时间、城市、渠道仍在 |
| 8 | 按供应商看 | 仍订单数、7 月；维度含 supplier_name |
| 9 | 只看杭州阳光假期门店 | 仍订单数、7 月、供应商维；**增加** 渠道名=杭州阳光假期门店 |

| 5 | 只看门票 | 加品类=门票 |

### 链路 C（时间确认穿插后必须能接着追问）

若第 0 轮因缺时间进入确认：确认回复算剧本内步骤，**不占用 10 次追问名额**；确认后快照必须已带时间，再开始 10 次追问。10 次从「按渠道拆」起，期望与链路 A 的 1～10 同类：先有「近 14 天订单数」确认窗口，再拆渠道、只看用车、换城市、去掉用车、改成 2026-08、加供应商、改 GMV、按品类、只看酒店、改回订单数。每轮同样做快照+SQL 核对。

### 链路 D（reset 与新问题）

前 5 次追问走 GMV 继承；第 6 次用户说完整新问题「2026年7月按供应商看取消率」必须 **reset**，不得残留上一轮渠道维；第 7～10 次在新快照上再继承（按城市、只看用车、改成订单数、再按渠道）。reset 轮若仍带着旧渠道维 = 失败。

### 链路 E（应澄清 / 应拒绝）

混入：库表问题、谢谢、写操作、无指标的「再拆一下」（若当时无快照）。有快照时「再拆一下」应澄清缺维度，不得瞎选一维出数。10 次中按剧本标注应出数或应澄清，对不上即失败。

## 每轮核对清单（执行者逐轮勾）

1. `session_id` 未变。
2. SQL 含 `tb_orders`，不含其它业务表顶替（导览/闲聊/拒绝轮除外）。
3. 指标：gmv 则有成交额聚合及默认状态；order_count 为计数；cancel_rate 为取消/退款相对全部的比率语义，不能把取消率查成 GMV。
4. 本轮要求的维度出现在 GROUP BY 或等价处；要求去掉的维不得残留。
5. 本轮要求的筛选值出现在 WHERE；要求去掉的筛选不得残留。
6. 时间谓词落在期望闭区间（允许日期边界写成当日 23:59:59）。
7. Outcome 与是否真有数据一致。
8. 阶段一还要能指认本轮经过 QueryHarness。

全部勾上才记该轮通过。
